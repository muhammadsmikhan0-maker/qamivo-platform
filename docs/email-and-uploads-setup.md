# Qamivo email, messaging and image-upload configuration

**Status date:** 25 October 2026  
**Application:** https://qamivo-platform.netlify.app  
**Implementation branch:** `chore/all-in-one-roadmap-ci`  
**Safety:** This feature work must pass CI and a Netlify Deploy Preview before production is considered verified. No credentials belong in Git or in chat.

## 1. Transactional email — required provider setup

The implementation uses the Resend HTTPS API from Netlify Functions and records attempts in the existing Netlify Database. It does not claim email is operational until the following secrets and sender are configured.

In Netlify → Project configuration → Environment variables, add values scoped to **Functions** for the `qamivo-platform` site:

| Variable | Required | Purpose |
| --- | --- | --- |
| `RESEND_API_KEY` | Yes | Secret provider API key from the approved Resend account |
| `QAMIVO_FROM_EMAIL` | Yes | Verified sender, e.g. a sender address at a domain the owner controls |
| `QAMIVO_APP_URL` | Recommended | Canonical HTTPS application URL used in email links |
| `RESEND_WEBHOOK_SECRET` | Yes for delivery states | Signing secret for the Resend webhook |
| `QAMIVO_ADMIN_EMAIL` | Optional | Confirmed owner address for job-posting alerts and admin-only email test |

Do not paste secret values into GitHub, issues, documentation, client-side code or this chat. After adding or changing function-scoped values, redeploy so the Functions runtime receives the new configuration.

### Domain authentication

1. In the owner-controlled Resend account, add and verify the chosen sending domain.
2. Copy the exact DNS records generated by Resend into the authoritative DNS host for that domain. Configure the displayed SPF and DKIM records; do not invent hostnames or values.
3. Publish a reviewed DMARC TXT record at the domain's `_dmarc` name. Choose a policy and reporting addresses suitable for the owner's existing mail environment; do not publish an aggressive policy before confirming that legitimate senders are covered.
4. Wait for the provider dashboard to report verification. Record the actual verification result before calling email production-ready.
5. Configure a Resend webhook pointing to `https://qamivo-platform.netlify.app/api/webhooks/resend` (or the later owner-approved custom domain). Subscribe to `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.opened` and `email.clicked`, if offered by the provider UI. Save the webhook signing secret as `RESEND_WEBHOOK_SECRET`.

The webhook verifies the timestamp and signature before changing an `email_events` row. A status of `sent` means the provider accepted the request; it does **not** prove that a mailbox accepted or displayed the message. The signed webhook must report delivery to support that conclusion.

### Safe email test

After configuration and redeploy, sign in with a verified account whose email matches `QAMIVO_ADMIN_EMAIL`, then issue a same-origin POST to `/api/email/test` while authenticated. The endpoint is restricted to that configured administrator email and reports provider acceptance separately from final delivery. It will return an error if provider settings are absent or the request fails; it must not be used as a public test endpoint.

### Identity registration and recovery

Netlify Identity handles its own confirmation and password-recovery links through the Identity provider/dashboard. Review the Identity settings at `https://app.netlify.com/projects/qamivo-platform/identity` and test registration, confirmation, recovery and reset on a Deploy Preview. Those built-in messages are separate from the Resend transactional sender above. Numeric OTP delivery is **not implemented** in the current app; no hardcoded or simulated OTP should be used.

## 2. Email events currently wired

- Welcome email when a member creates their first profile, if a provider and sender are configured.
- Administrator notification after a project is published, if `QAMIVO_ADMIN_EMAIL` is set.
- Project owner notification after a proposal is submitted.
- Freelancer notification when the owner shortlists or declines a proposal.
- Conversation notification when a new in-app message is stored.
- Provider status events captured by the signed webhook.

Orders, payments, invoices, contracts, deliverables, revisions, company team invitations and support tickets do not yet exist as operational workflows in this milestone, so no notification for those missing modules is claimed.

## 3. In-app messaging

The new server function is served at `/api/comms/*`. Conversations and messages are persisted in the relational database. Only verified members participate, and the initial flow allows a project owner and a freelancer who submitted a proposal for that project to start a conversation. The dashboard polls for new messages every few seconds and records unread counts. Message content and image attachments are not publicly indexed.

End-to-end acceptance on a Deploy Preview must still verify two separate accounts, create a proposal, start a conversation, send and receive messages in both directions, reload and sign back in, unread count changes, private attachment access, participant-only authorization, rate limiting, and email notification status.

## 4. Profile photos and image references

The upload API uses Netlify Blobs for object bytes and Netlify Database for metadata. In production it uses a durable site-wide store; preview uses a separate store to avoid touching production uploads. The API validates file signatures against JPEG, PNG, WebP and GIF, limits each file to 5 MB, requires a verified account and checks same-origin writes. SVG and non-image files are rejected.

UI slices currently include:
- Profile picture upload/preview/framing/removal in `/account`; the profile image displays on public profiles only when the profile is public.
- Up to five private reference images on the new project form; owner and project proposers can view them.
- Private image attachment sending and retrieval in in-app conversations.

The upload storage API has reserved purposes for portfolio, company logo, support attachment, learning content and ad creative, but those product forms/workflows are not yet implemented. Do not describe all upload use cases as complete until each has a real UI and its access-control test.
